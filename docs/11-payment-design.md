# 11 — Payment & Subscription Commerce Design

Stripe runs in **test mode** in every environment for this portfolio build. The design is production-grade, so switching to live mode means changing keys, the webhook endpoint and the Stripe Tax registration only.

---

## 1. Principles

1. **The server is the only price authority.** The client never sends amounts. Every quote is recomputed from the DB.
2. **Webhooks are the source of truth** for payment and subscription state (ADR-003). Redirects are UX, not state.
3. **Everything is idempotent.** Stripe requests use idempotency keys derived from our IDs, and webhook events are deduplicated by event ID.
4. **Stock is reserved before money is taken** (ADR-004).
5. **Minimal PCI scope (SAQ A).** Card data only ever lives inside Stripe's iframe.

---

## 2. Stripe objects & mapping

**API version pinning (review R-05):** the Stripe SDK client is constructed with an explicit `apiVersion`, and the webhook endpoints are created with the same version. Several fields this design touches (invoice → payment intent, subscription period dates) moved between recent API versions. Upgrading the version is a deliberate PR with the recorded webhook fixtures re-captured. The M1.5 spike records the exact version and field paths in ADR-0011.

| Nura concept               | Stripe object                                                                                       | Mapping                                                                           |
| -------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Customer (user)            | `Customer`                                                                                          | `User.stripeCustomerId`, created lazily at the first checkout (`metadata.userId`) |
| Product variant            | `Product` (one per variant)                                                                         | `StripePrice.stripeProductId`                                                     |
| One-time price             | `Price` (one-time)                                                                                  | `StripePrice(purchaseType=ONE_TIME)`                                              |
| Subscription price         | `Price` (recurring `interval=week`, `interval_count` 4/8/12, amount = price × 0.85 rounded half-up) | `StripePrice(purchaseType=SUBSCRIPTION, intervalWeeks)`                           |
| Bundle (pre-built routine) | `Product` + `Price` for the bundle variant                                                          | Components tracked only in our DB                                                 |
| Checkout                   | `Checkout Session` (`ui_mode: embedded`)                                                            | `Order.stripeCheckoutSessionId`                                                   |
| Order-level discount       | Ephemeral `Coupon` (`amount_off`, `duration: once`, `max_redemptions: 1`) created per session       | `Order.discountCents`                                                             |

| Refund                     | `Refund`                                                                                            | `Refund`                                                                          |

### 2.1 Catalogue sync (`stripe/product.sync` Inngest function)

- Triggered on product publish, variant price change and variant archive.
- Upserts the Stripe Product per variant (`metadata.variantId`, `metadata.sku`) and ensures 4 active prices (1 one-time + 3 recurring).
- **Price change:** Stripe Prices are immutable → create new prices, mark the old ones `active=false` in Stripe and in `StripePrice`. **Existing subscriptions keep their price (grandfathered).** A P2 admin tool migrates subscribers with a 30-day email notice.
- **Safety net:** at checkout, if an active `StripePrice` is missing for a line, `ensurePrice()` creates it synchronously (with an idempotency key `price:{variantId}:{type}:{interval}:{amount}`).


### 3.2 Amount integrity check

On `checkout.session.completed`, the handler asserts `session.amount_subtotal − session.total_details.amount_discount + amount_shipping == order.totalCents − order.taxCents`. If the check fails (for example the catalogue price changed mid-session), the order is still marked paid (the customer paid what Stripe showed) but is flagged `needsAttention = true` with reason `amount_mismatch`, and Stripe's amounts are stored.

## 4. Pricing engine (`features/pricing/server/engine.ts`)

A pure function: `quote(cart, context) → Quote`. The context includes `user`, `isFirstOrder`, `coupon`, `settings` and `now`. It is heavily unit-tested with table-driven cases and property-based tests (fast-check: totals never negative; line allocations sum to the total discount).

### 4.1 Rule pipeline (fixed order)

| #   | Rule                      | Applies to                                                     | Detail                                                                                                                                                                                                                                                                                    |
| --- | ------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Base price**            | All lines                                                      | `variant.priceCents × qty`. For bundles: the bundle variant price.                                                                                                                                                                                                                        |
| 2   | **Subscription discount** | SUBSCRIPTION lines                                             | 15% (`settings.subscription.discount_bp`); the line unit price becomes the subscription price (identical to the Stripe recurring price)                                                                                                                                                   |
| 3   | **Routine discount**      | Lines with the same `consultationId`, if ≥ 3 such lines remain | 10% on those lines, **first order only** (never on renewals). Combined line discount (steps 2+3) is capped at 25%.                                                                                                                                                                        |
| 4   | **Coupon**                | Eligible lines per coupon rules                                | Percentage (capped at `maxDiscountCents`) / fixed (≤ eligible subtotal) / free shipping. If `exclusive` and a routine discount exists → the engine applies **whichever saves the customer more** and returns `notice: "coupon_replaced_routine_discount"` or `"routine_discount_better"`. |
| 5   | **Shipping**              | Order                                                          | $0 if any subscription line **or** merchandise subtotal after discounts ≥ $60 **or** a FREE_SHIPPING coupon; else $6.50 (`settings.shipping.*`)                                                                                                                                           |
| 6   | **Tax**                   | Order                                                          | Estimated as "calculated at checkout" in the cart; actual from Stripe Tax                                                                                                                                                                                                                 |

### 4.2 Rounding & allocation

- All math is in integer cents. Percentages are in basis points: `discount = floor((amount × bp + 5000) / 10000)` (half-up).
- Order-level discounts (coupon) are **allocated to lines** by the largest remainder method, so that `Σ line.discountCents == order.discountCents` exactly. This is required for accurate partial refunds per line.
- In Stripe, steps 2 are expressed in the Price, and steps 3+4 in the single ephemeral `amount_off` coupon.

### 4.3 Quote output

`{ lines: [{lineId, unitPrice, discounts: [{kind, amount}], total}], subtotal, discounts: [{kind, label, amount}], shipping, taxEstimate: null, total, freeShippingRemaining, notices[] }`

## 5. Webhook processing

### 5.1 Pipeline (`/api/webhooks/stripe`)

```
raw = await req.text()
event = stripe.webhooks.constructEvent(raw, sig, secret)          → 400 on failure
inserted = INSERT INTO webhook_events (id=event.id, …) ON CONFLICT DO NOTHING
if !inserted and existing.status == 'processed' → 200 (duplicate)
handler = registry[event.type] ?? ignore
try { await handler(event) ; mark processed } catch { mark failed, attempts++ ; return 500 }  // Stripe retries up to 3 days
```

Handlers are **convergent**. They read the latest state from Stripe when ordering matters (for example `stripe.subscriptions.retrieve` in subscription handlers), because Stripe does not guarantee event order.

### 5.3 Ordering & race handling

| Race                                                                        | Resolution                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `customer.subscription.created` arrives before `checkout.session.completed` | The subscription handler upserts by `stripeSubscriptionId`, finds the user via `metadata.orderId` → Order.userId; the checkout handler then links it. Both are idempotent.                                                                                                                                                                                                                     |
| The customer's return page loads before the webhook                         | The page polls `/orders/by-session/:id` (see 04-C7). The server can also **proactively** process: if the session status is `complete` and the order is still pending, the return page calls `OrderService.markPaidFromSession(sessionId)`, the same idempotent function the webhook calls (retrieving the session from Stripe for verification). The first caller wins; the second is a no-op. |
| A reservation expires (35 min) just before the payment completes            | Covered by the shortfall check in `markPaid`, which flags the order. It never auto-cancels a paid order.                                                                                                                                                                                                                                                                                       |
| Sweeper releases reservations while payment is in flight                    | The sweeper only releases reservations of orders whose Stripe session is `expired` (verified via the API for orders newer than 2 h), and otherwise waits.                                                                                                                                                                                                                                      |

## 6. Coupons: validation rules (`features/coupons/server/service.ts`)

A coupon is valid for a cart when **all** of the following hold:

1. It exists, `isActive`, not archived.
2. `startsAt ≤ now < expiresAt` (if set).
3. `redemptionCount < maxRedemptions` (if set). Re-checked under `FOR UPDATE` at session creation and at markPaid.
4. The per-customer count (by userId, or by email for guests at markPaid) is < `perCustomerLimit`.
5. `firstOrderOnly` → the user/email has no PAID orders.
6. The eligible lines subtotal is ≥ `minSubtotalCents`.
7. There is ≥ 1 eligible line per `appliesTo` (`routines_only` = lines with consultationId or bundle products).
8. Subscription lines are eligible only if `appliesToSubscriptions` (first invoice only).

Failure reasons map to user-facing copy (e.g. `min_subtotal` → "Add $8 more to use this code").
**Guest email edge:** limits 4 and 5 can only be checked by email after Stripe collects it. At markPaid, if a guest violates the per-customer limit, the order is still honoured (the customer already paid). The redemption is logged and `needsAttention` is set with `coupon_limit_exceeded` for marketing's visibility. This is an explicit, documented business trade-off.

## 8. Refunds

1. Staff submits a refund (amount, lines, restock, reason). The permission and the limit are checked (Support ≤ $50 cumulative per order).
2. Validation: `amount ≤ order.totalCents − order.refundedCents`; line quantities ≤ `quantity − refundedQuantity`.
3. Insert `Refund(PENDING)` → `stripe.refunds.create({ payment_intent, amount, reason: mapReason, metadata: { refundId, orderId } }, { idempotencyKey: 'refund:' + refund.id })`.
4. The webhook confirms → SUCCEEDED → order `refundedCents`, `paymentStatus` → restock movements (if flagged) → email.
5. Renewal orders are refunded against their invoice's payment intent in the same way.
6. Cancelling before shipment = full refund + restock + `status=CANCELED`.

## 10. Reconciliation & reporting

- **Nightly `stripe/reconcile`:** lists Checkout Sessions, Invoices and Refunds from the last 48 h via the Stripe API and compares them with the DB (orders paid, renewal orders created, refunds recorded). Any drift → the missing webhook is reprocessed through the same handler, and staff are alerted if drift persists.
- **Accounting export:** the orders CSV includes the Stripe payment intent, fees (from balance transactions, P2), tax and discounts.

## 11. Payment security checklist

- [ ] Publishable key only on the client; the secret key and webhook secret are server-only env vars (validated at boot).
- [ ] Restricted API key for runtime with only the needed permissions (Checkout, Customers, Subscriptions, Invoices, Refunds write; Products/Prices write for the sync job).
- [ ] No amounts accepted from the client; metadata is never trusted for amounts, only for IDs, which are re-loaded from the DB.
- [ ] Webhook signature verification with raw body; replay protection via event ID.
- [ ] Idempotency keys on every write call.
- [ ] CSP allows `js.stripe.com`, `*.stripe.com` frames and `api.stripe.com` connect on `/checkout` only.
- [ ] Stripe Radar default rules on; block if the CVC check fails.
- [ ] Refund actions require permission, limits, step-up reverification (> $100) and an audit log.
